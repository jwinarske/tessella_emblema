# `draw_cost` and `first_pixel` on an i.MX8M Plus (VeriSilicon GC7000UL).
#
# `root@wafer-imx8mp.lan`, NXP Yocto, aarch64, glibc 2.39, 4 cores, idle at load 0.00.
# Vulkan loader 1.3.275 with NXP's ICD at /etc/vulkan/icd.d/imx_icd.json naming
# `/usr/lib/libvulkan_VSI.so.1` (driver 6.4.11). The loader warns that it "supports
# Vulkan 1.3, but only supports loader interface version 2" and lacks
# `vkEnumerateInstanceVersion`, so it is treated as a 1.0 ICD; the bench asks the entry
# point for a version rather than assuming one, and gets 1.0 here.
#
# # What this board found
#
# **Vivante's SPIR-V compiler segfaults on `OpCompositeConstruct` of a matrix.** Before
# the matrix-free form, the bench died with SIGSEGV and printed nothing; gdb put the fault
# in `VIR_Shader_CompositeConstruct` in `libVSC.so`, reached through `gcSPV_Decode` in
# `libSPIRV_viv.so`.
#
# That is the other half of Adreno's assertion on a `mat4x4` read from a storage buffer.
# One vendor refuses the matrix in the block and the other refuses rebuilding one from
# columns, so the form that satisfies both is to have no matrix type at all and write the
# multiply as the four multiply-adds it is. See `preamble::MATRIX`.
#
#                     record p50               per draw
# shape          desktop   pi5  sa8155p imx8mp   desktop   pi5 sa8155p imx8mp
# instance           9.6  49.4    736.1  294.4    0.0150 0.077  1.1502 0.4600
# push              11.5 363.5*  1080.6  363.5    0.0180 0.568  1.6885 0.5680
# buffers           24.0 681.2*  1350.0  445.1    0.0375 1.064  2.1094 0.6955
# descriptors       26.1 681.2   1698.3 1276.9    0.0407 1.064  2.6536 1.9951
#
# All times in microseconds. (* the pi5 `push` and `buffers` rows are from the run in
# raspberry-pi-5.txt; only `instance` and `descriptors` were re-taken here.)
#
# Recording is cheaper here than on either other board, which is worth noting against the
# habit of treating an i.MX8M as the slow one: 0.46 us a draw against the sa8155p's 1.15.
# The board is also genuinely idle, where the sa8155p sits at load 13.
#
# # What is still unknown here
#
# **The verification's control does not draw on this device, so the slot is unproven.**
# The probe draws one triangle over the whole of clip space with an identity matrix in slot
# zero and `firstInstance` of zero -- the control -- and reads the center pixel back. On
# the other three devices that is green. Here it is the clear color, which means the probe
# cannot draw at all on this driver rather than that the base instance was dropped.
#
# That distinction is the whole reason the control exists. Without it the run reported
# "SLOT NOT DELIVERED" and the honest reading of that was a false accusation against a
# shipping driver.
#
# What it is not, each ruled out by a run:
#
# - **Not the readback, and not a stale tile-status clear.** The pixel read back is exactly
#   the clear color, so the clear reaches memory and the copy reads it. That also rules out
#   the resolve kick the drm-cxx work on this board documents: there is nothing stale to
#   resolve, the draw simply contributed no fragment.
# - **Not the storage buffer.** With the vertex stage's block read replaced by the raw
#   attribute -- a constant position, no storage buffer touched -- the target is still the
#   clear color. This matters well beyond the probe: every block in this crate is read from
#   a storage buffer indexed per drawable, so an SSBO read that returned zeros here would
#   be a blocker for the design on this board rather than a fault in a bench. It is not
#   that.
# - **Not the image's tiling.** A linear color attachment, which this driver offers, leaves
#   the pixel unchanged.
# - **Not the loader.** Opening the ICD directly with `TSL_VULKAN_LIB` changes nothing.
#
# So the clear writes, the copy reads, the vertex positions need no memory, and still no
# fragment is produced. Whatever remains is in this probe's own render setup against this
# driver -- the render pass, the framebuffer, or the draw -- and not in anything the
# renderer depends on. The drm-cxx work has Vulkan drawing and scanning out on this exact
# board, so its example setup is where to compare against next.
#
# So: the timing is sound, the compiler fix is confirmed, and `firstInstance` is unverified
# here and verified on the other three.
#
# # What one vertex-stage DEM read costs (tessella#324)
#
# The one measurement this board does deliver, and it is the interesting one:
#
#   control  4343.5 us
#   sampled  7816.1 us
#   delta    3472.6 us over 1,048,576 fetches = 3.312 ns a fetch
#
# **Twelve times Adreno's 0.262 ns, and the control needs no readback to be trustworthy** --
# it is a submit-to-fence time, not a pixel. A vertex-stage sampled read is genuinely
# expensive on this part: a million of them is 3.5 ms. So where terrain's per-vertex fetch
# is a rounding error on Adreno, on Vivante it is a cost worth designing around, and this
# is the board where moving the raise off the vertex stage would actually pay.

#   background_pattern      drew          drew
#   both_as_glyph           drew      segfault

#   fill_outline        segfault      segfault
#   fill_pattern            drew          drew

#   raster              segfault      segfault
#   raster_adjusted     segfault      segfault
#   symbol_below            drew      segfault
#   symbol_icon             drew          drew
#   symbol_sdf              drew      segfault
#
# Enumerate per case with `TSL_ONLY`. A full run dies at the first segfault and loses
# every buffered line before it, so it reports nothing and undercounts everything.
#
# # #326 fixed one pixel and cost six modules
#
# `background` went from a wrong pixel to correct, and six families went from drawing to
# segfaulting. That change rewrote declared types from the shader text instead of
# `AttributeInfo`, which turned many `Float` declarations into `Float2`, so a body that read
# a scalar attribute now reads a component of a vector one.
#
# Why that crashes is **not** established. The trigger below is a composite built from a
# scalar loaded out of a *storage buffer*, and these are vertex attributes. The `fill`
# bisection further down fails on `in.fill_opacity.y`, which is the same shape one step
# over, so the rule plausibly covers any direct interface load -- but no rung tested a
# vertex attribute, so that is a guess and not a measurement. Filed on tessella#330.
#
# # The crash
#
#   #0  libVSC.so
#   #1  VIR_Shader_CompositeConstruct   libVSC.so
#   #2..4  gcSPV_Decode                 libSPIRV_viv.so
#   #5..7  libvulkan_VSI.so.1           (pipeline creation)
#
# It is in shader compilation, not in the clear, the readback or the linear attachment:
# `background` exercises all three and passes.
#
# # The trigger
#
# An `OpCompositeConstruct` whose operand is a scalar loaded directly out of a storage
# buffer. Bisected 2026-10-04 with throwaway cases in the oracle, each holding the blocks,
# textures, attributes and vertex stage fixed and varying one thing. All twelve build and
# draw on RADV first.
#
#   the composite's operands                                    GC7000UL
#   props.a, props.b, props.c, 1.0 -- direct loads              segfault
#   vec3<f32>(props.brightness_low)                             segfault
#   vec3<f32>(b, b, b), b a direct load                         segfault
#   mix(v4, v4, props.fade_t) -- naga splats the scalar         segfault
#   props.a * 1.5, props.b * 1.5, props.c * 1.5, 1.0            builds
#   dot(c, props.spin_weights.xyz), ... -- computed             builds
#   vec4<f32>(props.spin_weights.xyz, 1.0) -- vector member     builds
#   vec3<f32>(0.25) -- constant                                 builds
#   a * (1.0 - f) + b * f -- no composite at all                builds
#
# The scalar's provenance decides it. Any arithmetic between the load and the constructor
# compiles, as does a vector member, as does a constant. Writing a splat out longhand does
# not help, so it is not the splat syntax. Two hypotheses died here: a repeated operand is
# not it -- three distinct loads crash too -- and neither is the splat.
#
# `mix(vecN, vecN, scalar)` is the idiom that makes this common, since naga lowers the
# scalar to a splat. The workaround is per-expression: keep a direct scalar load out of a
# vector constructor. Whether to apply it across 18 families is open on tessella#330.
#
# # What the earlier reductions were worth
#
# Against `fill`, before #326:
#
#   both attribute reads replaced by constants                        builds
#   the `Float4` read kept (`mix_color(in.fill_color, ...)`)           segfault
#   the `Float2` read kept (`in.fill_opacity.y`, no mix at all)        segfault
#   neither read, `mix(0.0, 1.0, drawable.opacity_t)` instead         builds
#
# Those stand as measurements, but the rule drawn from them -- that reading a `Float2` or
# `Float4` attribute is enough on its own -- does not hold: `background_pattern`,
# `heatmap`, `line_pattern`, `fill_pattern` and `symbol_icon` read them and build. The
# `mix` in each failing row is the composite above.
#
# The `raster` reduction was wrong. It recorded one storage block, a minimal body and two
# `Short2` attributes as segfaulting, with `background` as the control. Rebuilt that way,
# it builds and draws: raster's two blocks, two textures and two `Short2` attributes with
# a minimal body pass. The control had changed the drawable block as well as the attribute
# count, so it isolated neither. Two `Short2` attributes are fine -- `color_relief` and
# `hillshade` declare exactly that and build, `heatmap_texture` declares three and passes.
# The claimed third trigger, `background_pattern` segfaulting on a single `Short2`, is
# withdrawn: it builds.
#
# # Float vertex attributes read zero
#
# Not a capability gap, not an offset or stride error, and not a varying artifact. One
# measurement rules out each.
#
# `vkGetPhysicalDeviceFormatProperties` on the board, for every format the ABI's declared
# types map to -- all ten report `VERTEX_BUFFER`:
#
#   Short2 -> R16G16_SINT          Float2 -> R32G32_SFLOAT
#   Short4 -> R16G16B16A16_SINT    Float3 -> R32G32B32_SFLOAT
#   UShort2 -> R16G16_UINT         Float4 -> R32G32B32A32_SFLOAT
#   UShort4 -> R16G16B16A16_UINT   Float -> R32_SFLOAT
#   UByte4 -> R8G8B8A8_UINT        Int -> R32_SINT
#
# So the driver claims the format and then returns nothing. The probe never calls
# `device::check_vertex_formats`, which is its own gap, but it would not have caught this.
#
# Next, offset and stride. A rung whose every float in the stream is the same value, so any
# wrong offset or stride *inside* the buffer still reads it:
#
#   vec4<f32>(in.heatmap_weight.x, in.heatmap_weight.y, 0.2, 0.6), stream all 0.75
#
#   RADV       [191, 191, 51, 153]
#   GC7000UL   [  0,   0, 51, 153]
#
# Both constants land and both attribute components are zero, so the fetch did not happen.
#
# Last, the stage. A rung where the attribute decides geometry rather than travelling
# through a varying -- at 0.75 the triangle leaves the viewport, so the sampled pixel is
# the clear:
#
#   if in.heatmap_weight.x > 0.5 { p = p + 10000.0; }
#
#   RADV       pass, the pixel is the clear and the triangle moved
#   GC7000UL   [255, 255, 255, 255], the triangle stayed
#
# The comparison was false, so the attribute was zero before any interpolation. Nothing in
# the fragment stage is involved. The `Short2` position in the same module arrives -- the
# geometry is placed correctly, which is why there is a pixel to read. Integer vertex
# attributes fetch and float ones do not.
#
# This is what most of the wrong pixels are. Five of the eight families that build and draw
# wrong read a `Float2` or `Float4`: `background_pattern`, `heatmap`, `line_pattern`,
# `fill_pattern`, `symbol_icon`. It does not cover `color_relief`, `hillshade` or
# `hillshade_prep`, which declare only `Short2` and still draw wrong; those are separate and
# uninvestigated.
#
# It does not explain #326's six regressions either. Those went from drawing to
# *segfaulting*, and the three rungs above all build -- a direct scalar load from a vertex
# attribute into a composite compiles, where the same shape from a storage buffer does not.
#
# # tessella#327 costs nothing here
#
# Rebuilding `color_relief` with the texture coordinate omitted from the vertex input and
# derived from the position, as mbgl's Vulkan shader does, changes neither the build nor
# the pixel: `[128, 128, 128, 128]` against `[10, 90, 55, 128]` either way. The family
# already compiles on this driver. The earlier note here that the over-declaration decides
# whether it compiles was wrong.
#
# Its wrong pixel is a separate defect. `[128, 128, 128, 128]` is ramp texel 0, white, at
# the case's half opacity, which is what an elevation at or below the first stop selects --
# so the DEM sample reads as zero here and as texel (1, 1) on RADV from the same binary.
#
# # What this does not say
#
# That the shaders are wrong. The same modules draw 24 for 24 on Adreno and on two desktop
# drivers, bit-identical, and the pixels are derived from mbgl's own arithmetic.

#   case              layer off   layer on
#   both_as_glyph      segfault   built, reads the clear
#   both_as_icon       segfault   built, reads the clear
#   extrusion_dim      segfault   built, [7, 7, 7, 255] against [125, 125, 125, 255]

#   symbol_sdf         segfault   built, reads the clear

# And the "before #326" column cannot be rebuilt any more. Reverting the six attributes the

# `idFillExtrusion*`/`idSymbol*` to `Float`, 17 sites -- fails in **naga validation** for 17

# types: `cannot cast a vec3<f32> to a vec2<f32>`, and `paint_opacity`/`paint_base` called
# with a `vec2` where a `vec3` is required. tessella#330 is closed on that basis.
#
# # "Float vertex attributes read zero" is withdrawn
#
# The section above says integer vertex attributes fetch and float ones do not. They fetch.
# A quad whose `uv` is `(0.3, 0.7)` at every vertex, read in a vertex stage that takes its
# three attributes as **separate entry-point parameters**, reads exactly right on this part:
# `[166, 217, 153, 255]` at two sample points, the same as RADV. `attr/attr-flat.spv` in the
# crash repository, through `repro-attr.c`.
#
# What those rungs were reading is VIV-6. **A vertex entry point whose position is built
# straight out of the struct parameter the translator rebuilds loses the draw** -- naga
# emits `OpCompositeConstruct` of the input loads, `OpCompositeExtract` to read a member,
# and where that extract's result is an operand of the construct stored to `gl_Position`,
# no pixel is written. No crash and no validation message. 193-word module; the same extract
# through a `var`, times 1.0, by components, or as a separate parameter all draw, and it is
# identical with the layer on and off. Against a black clear a lost draw and a zeroed color
# are the same pixel, which is what made those rungs read as a failed fetch.
#
# It is not established for the families here: `vertex_main` in
# `family-mods/background_pattern.spv` has no construct whose operand is an extract, so the
# sixteen cases that draw nothing reach that by some other path. VIV-2 -- every extract from
# a rebuilt *fragment* input struct answering member 0 -- is the candidate for the wrong
# colors, and is confirmed in the vertex stage too (`attr/attr-mixed-read.spv`).
#
# # The `check_vertex_formats` gap is closed
#
# The section above notes that the probe never calls it. `first_pixel` calls it before the
# enumeration now.
#
# # `firstInstance` is verified here now, and it was this bench all along
#
#   firstInstance reaches the shader as slot 613
#
# The section above says the probe cannot draw on this device and that `firstInstance` is
# unverified here. Both were wrong, and so was the guess that followed them -- that the
# difference was this bench's render pass against the library's dynamic rendering. It was two
# stale constants in the bench, and the first of them makes the point this file keeps making
# about invalid usage:
#
# - **The verification pipeline declared `R32G32B32_SFLOAT` at location 0, stride 12**, which
#   is what `AttributeInfo` said for `idBackgroundPosVertexAttribute` until tessella#326 took
#   the declared type from the shader text and made it `Short2`. A format whose numeric type
#   differs from the shader input's is invalid usage --
#   `VUID-VkGraphicsPipelineCreateInfo-Input-08733`, "format (VK_FORMAT_R32G32B32_SFLOAT) at
#   Location 0 does not match vertex shader input type (vec2 of sint32)" -- and **no driver
#   reports it**: RADV drew nothing either, in the same state, and had been since #326. The
#   board was being read as the odd one out for something every device was failing.
# - **The slots were written 64 bytes apart**, which is `BackgroundDrawableUBO`'s own size.
#   The consolidated array pads every block to the widest family's stride, 96 here, so the
#   identity landed short of the slot the shader reads: a zero matrix, and no triangle.
#
# Both now come from the crate -- `device::{vertex_format, stride_of}` and `slots::stride` --
# so a table change cannot desync them again. The control draws and the slot check passes on
# RADV and on this board, which closes the elimination list above: not the readback, not the
# storage buffer, not the tiling, not the loader, not the render pass, and not the driver.
#
# The one thing that found it was the Khronos validation layer on the desktop. Run the bench
# under it whenever the ABI's declared types or the block strides move.
#

# different tessella ABI from the rows above, so the two are not a before and after:
#
#   instance 0.6135 us a draw, push 0.5691, buffers 0.7043, descriptors 2.0295
#   vertex fetch 3.310 ns, against 3.312 above -- the same number two weeks apart
