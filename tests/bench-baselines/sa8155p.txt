# `draw_cost` and `first_pixel` on an sa8155p (Adreno 640), against the desktop and the Pi 5.
#
# `sa81x5-guest`, a Yocto dunfell image, kernel 5.4.219, 6 cores, glibc 2.31. The board
# ships a vendor Vulkan stack with its own loader, which predates 1.3 and leaves no `icd.d`
# and no validation layer to debug with.
#
# Figures here are this crate's own and the open drivers': Mesa's turnip on this part, V3DV,
# RADV. The vendor stack appears only as capabilities it reports and constraints it imposed on
# the shaders.
#
# Reached over `adb`, which is the transport only: this is Linux, not Android. Push to
# /tmp and run.
#
# # The board is never idle
#
# Load average 13.5 on 6 cores before anything of ours starts -- the vendor stack. So p50
# over sixty frames is the only figure worth reading and the p95 and max columns are
# contention, not signal. `taskset -c 5` refused with EINVAL on one run and worked on
# another, so the numbers below are unpinned.
#
# # Building for it
#
# glibc 2.31 is older than any sysroot on the build host (the ARM GNU toolchain ships
# 2.42), and static musl is not available because `ash` reaches Vulkan through `dlopen`.
# zig supplies stub libs per glibc version, so it links what nothing else here can:
#
#   # wrapper: exec ~/.local/zig/zig cc -target aarch64-linux-gnu.2.31 "$@"
#   CARGO_TARGET_AARCH64_UNKNOWN_LINUX_GNU_LINKER=<wrapper> \
#     cargo bench --no-run --target aarch64-unknown-linux-gnu
#   objdump -T <bin> | grep -oE 'GLIBC_[0-9.]+' | sort -V -u   # must stay <= 2.31
#
# Cargo does not fingerprint the linker environment variable, so delete the binary before
# relinking or it keeps the old one and the floor check passes on a stale file.
#
# # What it took to get a pipeline at all
#
# Two things, both of which RADV and V3DV accept and this driver does not:
#
# A `mat4x4<f32>` read from a storage buffer is refused: pipeline creation returns
# `VK_ERROR_UNKNOWN`. Matrices are declared as four `vec4` columns for this reason; see
# `preamble::MATRIX`.
#
# And one SPIR-V module may carry one entry point. A module holding `vertex_main` and
# `fragment_main` is refused with no diagnostic whatsoever -- the assertion above only
# appeared once the modules were split, so the first failure hides the second.
#
# # What each row is
#
# 640 drawables recorded into one command buffer, 60 frames a shape, strictly additive:
# each row is the one above plus the state named.
#
#                     record p50               per draw
# shape          desktop   pi5   a640      desktop   pi5   a640
# instance           9.3  57.8   573.6      0.0146 0.090  0.8962
# push              14.5 636.8   829.3      0.0227 0.995  1.2958
# buffers           26.3 651.9  1027.5      0.0411 1.019  1.6055
# descriptors       29.6 656.1  1366.1      0.0463 1.025  2.1345
#
# All times in microseconds. The a640 column is **Mesa's turnip** on this board, re-taken
# 2026-10-20.
#
# # What the numbers say
#
# **The merge is not worth porting on any of the three.** The dearest shape costs 2.13 us a
# draw here against the Flutter GPU sibling's ~62 us a draw on its own board, half of which
# is Dart walking batches.
#
# **Per-draw state costs real money here and almost none on V3D.** Going from `descriptors`
# to `instance` is 2.13 to 0.90 us, about 0.79 ms over a 640-drawable frame. On V3D the
# same span is 1.025 to 0.090 and nearly all of it is the push constant alone, with buffers
# and descriptors free on top. So the arena and a shared descriptor set earn their place on
# Adreno for a reason V3D does not show, and `firstInstance` earns its place on both.
#
# The three share no ratio: 6x/44x/25x/22x for pi5 over desktop, and 62x/57x/39x/46x for the
# a640 over desktop. There is no scaling factor from a desktop measurement to a board one
# for command recording, which is the whole reason these files exist.
#
# # The slot moved to `firstInstance`, and it is verified here
#
# The four shapes were re-taken after that change; the table above carries the current figures.
#
# What matters more than the figures is that **`firstInstance` reaches the shader as slot 613**
# here, by readback. Adreno parts have had base-instance quirks and the failure mode is silent
# -- every drawable reading slot zero -- so the bench checks it on every device before it times
# anything, and it has passed here under both of this board's drivers.
#
# The spread between `instance` and `descriptors` is 1.24 us a draw, 0.79 ms over a
# 640-drawable frame, which is why the arena and a shared descriptor set are worth having
# here. On V3D the same span is 0.96 us and almost all of it is the push constant alone.
#
# # What one vertex-stage DEM read costs (tessella#324)
#
# A controlled pair: one draw of 1,048,576 vertices, the vertex stage either reading the
# elevation or not, everything else held equal -- same buffer, same block, same target, and
# a placement that puts every vertex outside the clip volume so neither variant rasterizes
# a fragment. Submit to fence, p50 of 20.
#
#   control  1556.9 us
#   sampled  1549.9 us
#   delta       0.0 us over 1,048,576 fetches = 0.000 ns a fetch
#
# Those are turnip's, re-taken 2026-10-20. An earlier run on the other driver reached the same
# conclusion with a small positive delta rather than none.
#
# **So the fetch is not what costs 38.9 ms.** At a cost indistinguishable from zero over a
# million fetches there is no frame-sized vertex count that reaches it: a pitched z14 cover is
# tens of tiles at 17,415 vertices a tile, so even a generous count of every raised vertex in
# such a frame lands in the low millions, and the dearest per-fetch figure either driver has
# produced here would still put that at a millisecond or two.
#
# The remaining candidates are all about the path to the read rather than the read: whether
# the image view or descriptor is re-bound per draw where GLES caches it -- terrain scenes
# bind a texture per tile, which is the merge blocker already recorded for them -- and the
# backend's own per-draw work.

# ---------------------------------------------------------------------------
# # The board draws, on Mesa's turnip (2026-10-20)
#
# #144 records that no bench in this tree can open a device here: `benches/common` asks for
# `VkPhysicalDeviceVulkan13Features::dynamicRendering`, and the vendor driver is a Vulkan 1.1
# stack with neither the feature nor `VK_KHR_dynamic_rendering`. That is a capability it
# reports and not a measurement of it. Nor can it be rebuilt -- it is a vendor binary from the
# BSP, not in AOSP and not open anywhere.
#
# Mesa's driver for this part can be built, and it has what the pass needs:
#
#   device                Turnip Adreno (TM) 640
#   api                   1.3.363
#   driverInfo            Mesa 27.0.0-devel (git-7f13762f3f)
#   device extensions     162
#   dynamicRendering      YES, and vkCreateDevice succeeds with the benches' own struct
#   wideLines             no, lineWidthRange 1.0..1.0 -- and the part lacks it under either
#                         driver, so that is the hardware rather than Mesa
#
# **`kgsl`, not `msm`.** The GPU here is only on `/dev/kgsl-3d0`; `/dev/dri/renderD128` is
# `msm_drm` for the *display* controller (`qcom,mdss_mdp`, `sde-kms`), so there is no msm DRM
# node for the GPU and turnip's msm backend has nothing to open.
#
#   meson setup build-a640 --cross-file a640.ini -Dbuildtype=release \
#     -Dvulkan-drivers=freedreno -Dgallium-drivers= -Dfreedreno-kmds=kgsl \
#     -Dplatforms= -Dglx=disabled -Degl=disabled -Dgbm=disabled -Dopengl=false \
#     -Dllvm=disabled -Dshared-glapi=disabled -Dgles1=disabled -Dgles2=disabled
#
# The board's own loader predates 1.3, so an instance asking for it fails whatever the ICD
# reports; Vulkan-Loader built from source beside turnip (1.4.365) is what makes it work. Both
# go in /tmp with the ICD json, which is where this board allows exec, and the run is
#
#   LD_LIBRARY_PATH=/tmp/turnip VK_ICD_FILENAMES=/tmp/turnip/freedreno_icd.json ./first_pixel
#
# Three shims were needed because the host's bare aarch64 cross toolchain has no target libc
# or libstdc++ of its own and the staged ones are newer than the board's glibc 2.31: a
# `libatomic_asneeded` linker script, a `libgcc.a` script pulling a real `libgcc_eh.a` beside
# it, and an object defining `__libc_single_threaded`, the `__isoc23_*` redirects and
# `_dl_find_object` -- the last returning -1 so the unwinder takes its pre-2.35 path. None of
# them is turnip's doing; they are what cross-building a 2026 toolchain against a 2020 glibc
# costs.
#
# ## first_pixel: 48 measured, 48 correct
#
# Every family in the 49-case probe draws the pixel the oracle derived, through the library's
# own pass. The 2026-10-03 run above was 24 of 24 with a render pass the probe owned itself;
# this is twice the cases and none of its own Vulkan.
#
# The 49th, `fill_outline_at_two`, is **not measurable** here rather than wrong: it samples the
# row below the line's own, which only the second pixel of mbgl's two-pixel outline covers, and
# `device::line_width` falls back to one pixel where the device reports no `wideLines`. The
# probe says so now instead of failing -- both gate devices have the feature and this part has
# it under neither driver. The other two line cases sample the line's own row and pass.
#
# ## pipelines_build: all six checks
#
#   depth-stencil format  D24_UNORM_S8_UINT
#   every pipeline        168 pipelines, all resident at once
#   the cache reuses      252 asks, 84 built, 168 modules
#   a handle per stage    two handles, vertex then fragment
#
# That last line is #139's per-stage split running on Adreno 640 **hardware**, which is new. It
# is not a verification of what #139 fixed: the vendor driver is what refuses one module for
# two stages, and turnip does not, so the arrangement is exercised rather than tested here.
#
# ## capture_frame: a real frame replays
#
# `real.tslcap`, a recorded Mercator view: 12 batches, 19 geometries, 7 families, **12
# pipelines from 7 modules**, 28 drawables, 28 draws, 0 undrawn, 0 unclipped, and no texel left
# at the clear. Not the 168 `pipelines_build` brings up -- `Cache` builds what the frame asks
# for, which is the number that matters for a first frame.
#
# The same capture on the Pi 5 draws `[234, 230, 221, 255]` over **533,544** texels against
# **533,541** here, with 6312 colors against 6236. Three texels and seventy-six colors between
# two GPUs on one recorded frame, which is rasterization and filtering rather than anything
# structural.
#
# ## Every other bench
#
# Fourteen more run here and all fourteen pass, which is the result: turnip's **kgsl** backend
# is the least-travelled path in any of this, since Mesa tests the msm one and this board has
# no msm GPU node. It handled the GENERAL-layout handoff, linear staging, host-visible blocks,
# stencil masks and a two-pass frame without a failure -- a_frame, a_mesh, block_buffers,
# clip_masks, depth_bands, descriptor_layouts, descriptor_sets, geometry_store, hand_off,
# instance_fetch, overdraw_cost, texture_images, two_passes and capture_frame.
#
# Five figures differ from the Pi 5's for the same code, and are written down so a reader
# comparing the two files does not read a difference as a change. Both are Mesa drivers:
#
#   `a_frame`'s second region runs on **S8_UINT** here and `D24_UNORM_S8_UINT` on V3D. Turnip
#   offers a standalone stencil format and V3DV does not, so `Attachment::StencilOnly` gets a
#   true stencil-only attachment on this part.
#
#   `descriptor_layouts` reports the widest set as six storage descriptors against a limit of
#   **16,777,216**. On V3D that limit is **8**, which is where
#   `descriptor-limits-are-unenforced` gets its two of headroom. The constraint belongs to the
#   gating target alone; this part has no opinion.
#
#   Allocation granularity: `geometry_store` round-trips 136 claimed bytes in **192** here and
#   768 on V3D; `texture_images` staging is 8192 then 9216 against 4160 then 5440;
#   `block_buffers` holds 128 bytes resident against 256. Each is an alignment the driver chose.
#
#   `overdraw_cost` saves **85.7%** of a sixteen-layer frame against V3D's 89% in #104 -- the
#   same early-out on a second part, which is what §11.7's depth-write split was for. The floor
#   with nothing drawn is 343.5 us a frame.
#
# ## What this does not say
#
# **Nothing about the vendor stack.** Both findings this board forced -- no `mat4x4` read from a
# storage buffer, and one entry point per SPIR-V module -- are recorded above, and turnip
# accepts what that driver refused. A run here says the shaders and the library are right on
# Adreno 640 hardware; it does not re-test the driver that ships on it.
#
# ---------------------------------------------------------------------------
# # What a pipeline cache is worth, and why the pass hands one over (2026-10-20)
#
# A driver owes nothing without a cache object: `vkCreateGraphicsPipelines` passed
# `VK_NULL_HANDLE` may compile the shader every time, and the specification does not ask it to
# keep anything. That is not a quirk of any one driver -- **RADV does it too** with its own
# caches out of the way (`MESA_SHADER_CACHE_DISABLE=true`, no cache object): `fs-alu` at 534 us
# cold and **453 us on every repeat**, recompiling each time.
#
# Which matters here because the two caches hold different things. `pipelines::Cache` holds a
# *pipeline* per `Key`, so it never asks for the same pipeline twice -- but a key carries the
# vertex layout and the permutation where a module is per family and surface. **The pass builds
# 168 pipelines out of 66 module pairs**, so about a hundred of them hand the driver shader text
# another pipeline has already compiled. A real frame is 12 pipelines from 7 module pairs, so
# five of its twelve.
#
# `tools/drvprof cache [path]` is what asks the question per driver, and `drvprof module` times
# real family module pairs rather than the 88-to-358-word synthetics:
#
#   turnip, Mesa's own caches disabled        first create   repeats
#   background       (1072 + 946 words)          3380 us      5.9 us
#   fill_extrusion   (1886 + 1039)                8116        6.2
#   line_sdf         (2885 + 1810)               14598        6.2
#
#   a cache object preloaded from a file         27..77 us for the first create
#
# V3DV honors a serialized cache as well -- 22,544 bytes for three pipelines, and reloading it
# in a new process turns a 1.6 ms first create into 3.4 us -- and keeps something even with no
# cache object, where RADV recompiles. So "no cache without a cache object" is per driver rather
# than a rule, and **the only safe assumption is to always pass one**, which #158 makes the pass
# do.
#
# `drvprof cache` answers it per driver for anyone who needs the figure.
#
# ---------------------------------------------------------------------------
# # ir3 leaves a long loop rolled, and that is not an ALU gap (2026-10-20)
#
# Worth recording because it is easy to read a slow number as weak code generation. Measured on
# turnip with `tools/drvprof`, GPU timestamps, min of fifteen:
#
#   256 dependent squarings, rolled loop       3158.2 us
#   the same arithmetic written flat            447.8 us
#
# Squaring rather than scaling because `acc * k + c` repeated is affine and collapses to one
# multiply-add, so the rolled/flat pair for *that* measures an optimizer instead.
#
# `IR3_SHADER_DEBUG=disasm` says what happened (`TU_DEBUG=shaderdb` no longer exists):
#
#   shader            instr   nops   loops
#   fs-const              5      0      0
#   fs-sq                30     15      1   <- 256 iterations, not unrolled
#   fs-sq-flat         1042    777      0
#   fs-tex              158      6      0   <- sixteen iterations, unrolled
#
# So ir3 unrolls a sixteen-iteration loop and leaves a 256-iteration one rolled, and the rolled
# form pays loop overhead on top of the stalls a dependent chain causes either way -- three
# quarters of the flat form's slots are nops too. **Nothing in these families loops 256 times**:
# the longest are a 3x3 kernel in `hillshade_prepare` and a sixteen-tap raster, and sixteen is
# the count ir3 unrolls. So this describes no shader this crate ships.
#
# ---------------------------------------------------------------------------
# # The GPU clock steps 257 to 500 MHz, which is worth a factor of two (2026-10-20)
#
# Every timing in this file is read against this, so it goes last and applies to all of it.
#
#   /sys/class/devfreq/2c00000.qcom,kgsl-3d0
#   governor               msm-adreno-tz
#   available_frequencies  500 427 345 257 MHz
#   min / max              257 / 500 MHz, and max_pwrlevel 0 -- nothing is capping it
#
# **Under a light load the governor never leaves the bottom step.** A parallel session sampling
# `cur_freq` every 20 ms across five runs of a Flutter cluster scenario -- about 4,300 samples --
# read 257 MHz every time, with `trans_stat` showing zero ms at any other step and
# `gpu_busy_percentage` at p50 16, max 25.
#
# **A saturating one reaches the top.** `drvprof fill` sampled the same way, 700 samples over
# two back-to-back invocations: 666 at 257 MHz, three at 345, four at 427 and **27 at 500**,
# with `trans_stat` at 500 MHz gaining 1,548 ms over those runs.
#
# And the same test in the two invocations, by GPU timestamp:
#
#                             run 1 (from idle)   run 2 (straight after)
#   fill: 1 draw, const            145.5 us              76.1 us          1.91x
#   alu: 1 draw, 256 mad          3156.7                1623.6            1.94x
#
#   500 / 257 = 1.95
#
# So a factor of two on this board is one devfreq transition, not driver behavior, heat or
# noise. What follows:
#
#   - Compare back to back in one sitting, and record which step you were on.
#   - Prefer `min` over `p50`: the fastest sample is the one least likely to span a transition.
#   - Read a wide spread as a transition rather than noise. `alu: 8 draws` has reported min
#     9697.7 against p50 13917.4 -- a 44% gap, which is the clock moving mid-series.
#   - A figure from an idle board is a 257 MHz figure. The first measurement after boot is the
#     slowest one you will ever take.
#
# **It does not rescale anything above.** Every cross-driver and cross-device comparison in this
# file was taken back to back within one sitting, and the figures that carry a driver name land
# on the bottom step for both sides -- which is checkable: turnip's 3156.7 here is the same
# number its column carries, and that is the 257 MHz value.
#
# Pinning is available and not taken: the governors on offer are userspace, powersave,
# performance, simple_ondemand and msm-adreno-tz, and `min_freq` is writable. Holding the top
# step would make every number repeatable and would also leave the board in a state the next
# user did not ask for.
