# `draw_cost` and `first_pixel` on an sa8155p (Adreno 640), against the desktop and the Pi 5.
#
# `sa81x5-guest`, Cockpit SDK(IVI) v12.9.0 (Yocto dunfell), kernel 5.4.219, 6 cores,
# glibc 2.31. Vulkan 1.2.198 through `/usr/lib/libvulkan_adreno.so` -- Qualcomm's own
# loader, so there is no `icd.d` and no validation layer to debug with.
#
# Reached over `adb`, which is the transport only: this is Linux, not Android. Push to
# /tmp and run.
#
# # The board is never idle
#
# Load average 13.5 on 6 cores before anything of ours starts -- the vendor stack. So p50
# over sixty frames is the only figure worth reading and the p95 and max columns are
# contention, not signal. `taskset -c 5` refused with EINVAL on one run and worked on
# another, so the numbers below are unpinned.
#
# # Building for it
#
# glibc 2.31 is older than any sysroot on the build host (the ARM GNU toolchain ships
# 2.42), and static musl is not available because `ash` reaches Vulkan through `dlopen`.
# zig supplies stub libs per glibc version, so it links what nothing else here can:
#
#   # wrapper: exec ~/.local/zig/zig cc -target aarch64-linux-gnu.2.31 "$@"
#   CARGO_TARGET_AARCH64_UNKNOWN_LINUX_GNU_LINKER=<wrapper> \
#     cargo bench --no-run --target aarch64-unknown-linux-gnu
#   objdump -T <bin> | grep -oE 'GLIBC_[0-9.]+' | sort -V -u   # must stay <= 2.31
#
# Cargo does not fingerprint the linker environment variable, so delete the binary before
# relinking or it keeps the old one and the floor check passes on a stale file.
#
# # What it took to get a pipeline at all
#
# Two things, both of which RADV and V3DV accept and this driver does not:
#
# A `mat4x4<f32>` read from a storage buffer makes the shader compiler assert --
# `matOpnd->isMatrix()` in its own CodeGenHelper.cpp -- and pipeline creation returns
# `VK_ERROR_UNKNOWN`. Matrices are declared as four `vec4` columns for this reason; see
# `preamble::MATRIX`.
#
# And one SPIR-V module may carry one entry point. A module holding `vertex_main` and
# `fragment_main` is refused with no diagnostic whatsoever -- the assertion above only
# appeared once the modules were split, so the first failure hides the second.
#
# # What each row is
#
# 640 drawables recorded into one command buffer, 60 frames a shape, strictly additive:
# each row is the one above plus the state named.
#
#                     record p50               per draw              submit p50
# shape          desktop   pi5   sa8155p  desktop   pi5  sa8155p  desktop  pi5  sa8155p
# instance           9.3  57.8     769.8   0.0146 0.090   1.203      25.9 104.0  1493.9
# push              14.5 636.8     985.8   0.0227 0.995   1.540      34.5 112.4  1510.4
# buffers           26.3 651.9    1234.5   0.0411 1.019   1.929      59.3 112.5  1501.7
# descriptors       29.6 656.1    1582.7   0.0463 1.025   2.473      58.8 112.3  1547.9
#
# All times in microseconds.
#
# # What the numbers say
#
# **The merge is not worth porting on any of the three.** The dearest shape costs 2.47 us a
# draw here against the Flutter GPU sibling's ~62 us a draw on its own board, half of which
# is Dart walking batches.
#
# **Per-draw state costs real money here and almost none on V3D.** Going from `descriptors`
# to `instance` is 2.47 to 1.20 us, about 0.81 ms over a 640-drawable frame. On V3D the
# same span is 1.025 to 0.090 and nearly all of it is the push constant alone, with buffers
# and descriptors free on top. So the arena and a shared descriptor set earn their place on
# Adreno for a reason V3D does not show, and `firstInstance` earns its place on both.
#
# The three drivers share no ratio: 6x/44x/25x/22x for pi5 over desktop, and
# 82x/68x/47x/53x for sa8155p over desktop. There is no scaling factor from a desktop
# measurement to a board one for command recording, which is the whole reason these files
# exist.
#
# # Re-run after the slot moved to `firstInstance`
#
# shape          record p50   per draw   submit p50
# instance            835.5     1.3055       1419.6
# push               1080.6     1.6885       1505.0
# buffers            1350.0     2.1094       1474.9
# descriptors        1724.1     2.6939       1510.4
#
# `firstInstance reaches the shader as slot 613` here too, by readback. Adreno has had base
# instance quirks and the failure mode is silent -- every drawable reading slot zero -- so
# the bench checks it on every device before it times anything.
#
# The spread between `instance` and `descriptors` is 1.39 us a draw, 0.89 ms over a
# 640-drawable frame, which is why the arena and a shared descriptor set are worth having
# here. On V3D the same span is 0.96 us and almost all of it is the push constant alone.
#
# # What one vertex-stage DEM read costs (tessella#324)
#
# A controlled pair: one draw of 1,048,576 vertices, the vertex stage either reading the
# elevation or not, everything else held equal -- same buffer, same block, same target, and
# a placement that puts every vertex outside the clip volume so neither variant rasterizes
# a fragment. Submit to fence, p50 of 20.
#
#   control  1575.8 us
#   sampled  1850.7 us
#   delta     274.9 us over 1,048,576 fetches = 0.262 ns a fetch
#
# **So the fetch is not what costs 38.9 ms.** Accounting for that figure at this price
# needs about 148 million reads in a frame, which is 8,500 tiles' worth of terrain mesh at
# 17,415 vertices a tile. A pitched z14 cover is tens of tiles. Even a generous count of
# every raised vertex in such a frame lands in the low millions, which is a millisecond or
# two.
#
# The remaining candidates are all about the path to the read rather than the read: whether
# the image view or descriptor is re-bound per draw where GLES caches it -- terrain scenes
# bind a texture per tile, which is the merge blocker already recorded for them -- and the
# backend's own per-draw work.

# ## pipelines_build: all six checks

# ## draw_cost under turnip, against the blob's own numbers

# ## What this does not say
#
# **Nothing about the vendor stack.** Both findings this board forced -- no `mat4x4` in a
# storage buffer, and one entry point per SPIR-V module -- are the blob's, and turnip accepts

# hardware; it does not re-test the driver that ships on it.
#
# ## How the driver was built
#
# Mesa main, cross-compiled for the board's glibc 2.31 sysroot, Vulkan driver only:
#
#   meson setup build-a640 --cross-file a640.ini -Dbuildtype=release \
#     -Dvulkan-drivers=freedreno -Dgallium-drivers= -Dfreedreno-kmds=kgsl \
#     -Dplatforms= -Dglx=disabled -Degl=disabled -Dgbm=disabled -Dopengl=false \
#     -Dllvm=disabled -Dshared-glapi=disabled -Dgles1=disabled -Dgles2=disabled
#
# **`kgsl`, not `msm`.** The GPU here is only on `/dev/kgsl-3d0`; `/dev/dri/renderD128` is
# `msm_drm` for the *display* controller (`qcom,mdss_mdp`, `sde-kms`), so there is no msm DRM
# node for the GPU and turnip's msm backend has nothing to open.
#
# The loader matters too: the board's is 1.2.198, so an instance asking for 1.3 fails
# whatever the ICD reports. Vulkan-Loader built from source alongside it (1.4.365) is what
# makes the 1.3 instance work. Both go in /tmp with the ICD json, which is where this board
# allows exec, and the run is
#
#   LD_LIBRARY_PATH=/tmp/turnip VK_ICD_FILENAMES=/tmp/turnip/freedreno_icd.json ./first_pixel
#
# Three shims were needed because the host's bare aarch64 cross toolchain has no target libc
# or libstdc++ of its own and the staged ones are newer than the board's glibc 2.31: a
# `libatomic_asneeded` linker script, a `libgcc.a` script pulling a real `libgcc_eh.a` beside
# it, and an object defining `__libc_single_threaded`, the `__isoc23_*` redirects and
# `_dl_find_object` -- the last returning -1 so the unwinder takes its pre-2.35 path. None of
# them is turnip's doing; they are what cross-building a 2026 toolchain against a 2020 glibc
# costs.
#
# ---------------------------------------------------------------------------
# # The two drivers, side by side (2026-10-20)
#
# `tools/drvprof` is a C probe that renders through a `VkRenderPass`, so it runs on **both**
# drivers -- the blob's missing dynamic rendering is what keeps `benches/` off it. One binary,
# one loader, two ICD paths, so the driver is the only variable. Five naga modules, one entry
# point each and no matrices, which is what the blob accepts.
#
# Two rounds of blob / turnip / turnip-without-Mesa's-cache, interleaved, load average 16.8.
#
# ## Pipeline creation: turnip wins by between three times and a thousand
#
#   microseconds, per vkCreateGraphicsPipelines
#
#   fragment shader     blob cold   blob warm    turnip cold   with its cache   turnip warm
#   fs-const  (88 w)      7816         3912         1159             162            5.4
#   fs-alu   (254 w)      6930         5986         1640              80            5.5
#   fs-tex   (358 w)     10870        10882         4691              91            5.4
#
# Three readings, in order of how much they matter.
#
# **The blob's warm column is its cold column**: create the same pipeline nine times and it
# compiles nine times. Turnip has two caches -- an on-disk one at
# `/home/root/.cache/mesa_shader_cache` and an in-process one -- and
# `MESA_SHADER_CACHE_DISABLE=true` is the only way to measure its compiler rather than its
# cache, so the `turnip cold` column above is with the cache **off**.
#
# **Corrected 2026-10-20: that is not a defect, it is Vulkan.** Those creates pass
# `VK_NULL_HANDLE` for `pipelineCache`, and a driver owes nothing without a cache object. RADV
# does exactly the same when its own caches are out of the way -- `MESA_SHADER_CACHE_DISABLE=true`
# and no cache object: 534 us cold against 453 p50 for `fs-alu`, recompiling every time. What
# the comparison above really shows is a difference in *defaults*: Mesa ships an implicit disk
# cache and Qualcomm does not. The question that matters to an application -- whether the blob
# honors a `VkPipelineCache` it is handed -- is a separate one, and `tools/drvprof cache`
# answers it.
#
# **Answered for two drivers, open for the blob** (2026-10-20): RADV and V3DV both honor a
# serialized cache across processes, dropping a first create from 1.6 ms to 3.4 us, and V3DV
# keeps something even with no cache object where RADV recompiles. The blob's row needs a run on
# this board. `raspberry-pi-5.txt` has the table.
#
# **Compiling, turnip is 3 to 7 times faster**: 1.6 ms against 6.9 for the ALU shader, 4.7
# against 10.9 for the sampling one. Both compilers slow down with shader size, turnip from 1.2
# to 4.7 ms and the blob from 7.8 to 10.9.
#
# **With its cache, turnip is 5 us.** For this crate that is the difference between ~168
# pipelines costing a second and a half of compile on every process start and costing nothing
# the second time a device is opened. `vkCreateShaderModule` is noise either way: 3.3 us cold
# for the blob, 7.0 for turnip.
#
# ## Recording: turnip is nearly four times cheaper a draw
#
#   vkCmdDraw                 blob 0.1102..0.1285 us      turnip 0.0293..0.0301 us
#   vkCmdBindDescriptorSets   blob 0.0188..0.0418 us      turnip 0.0212..0.0220 us
#   instance + device + pass  blob 15.1..23.8 ms          turnip 20.8..24.9 ms
#
# The draw figure is the one `draw_cost` already saw from the other side: that bench records a
# fifth cheaper under turnip, and this says why. Descriptor binds and device creation are a
# wash.
#
# ## GPU work: turnip's fragment ALU is 40% behind, and nothing else is
#
#   microseconds, GPU timestamps, min of fifteen, both drivers measured back to back
#
#   pass                                   blob    turnip   turnip vs blob
#   fill 512x512, 1 draw, constant         72.9      76.1      4% slower
#   fill 512x512, 8 draws, constant       302.3     283.9      6% faster
#   256 dependent mads, 1 draw           1159.1    1623.6     40% slower
#   256 dependent mads, 8 draws          8934.5   12612.0     41% slower
#   16 samples a fragment, 1 draw         543.2     708.9     31% slower
#   16 samples a fragment, 8 draws       4075.0    4144.7      2% slower
#   1M degenerate vertices               1052.0    1058.6      1% slower
#   4M degenerate vertices               4099.5    4106.3      0% slower
#
# **Fill rate, vertex rate and warm sampling are the hardware's**, and the two drivers are
# within a few percent of each other on all three. The vertex rows are the sharpest: 1052
# against 1058 and 4099 against 4106, which is the part's primitive rate showing through both.
#
# **Fragment ALU is turnip's weak point here, by 40%, at both scales.** The same SPIR-V, the
# same 256-deep dependent chain of a multiply and an add; ir3 takes 1.4x the time Qualcomm's
# E031 compiler does. The obvious suspect is multiply-add fusion -- 256 mads against 512
# separate instructions would be 2x, and 1.4x is what partial fusion would look like -- but
# that is a guess until someone counts instructions, which `TU_DEBUG=shaderdb` would do.
#
# **Cold sampling is 31% behind and warm sampling is not**, which makes it a cache-warming
# difference rather than a sampler-rate one: the blob scales 7.5x from one draw to eight and
# turnip 5.8x, so turnip is getting more out of the second draw onward.
#
# ## A caveat that cost two rounds to find
#
# The blob's fragment numbers **halved between round one and round two** -- 140.5 us then 72.9
# for the same constant fill, 2253.7 then 1159.1 for the same ALU pass -- while turnip's moved
# by less than half a percent across four runs, and the vertex rows did not move for either.
# That is the GPU clock ramping, and it is why the table above is the min of fifteen within a
# round where both drivers ran back to back. A single comparison taken after an idle board
# would have read turnip as **twice as fast** at fragment work, and it is not.
#
# ---------------------------------------------------------------------------
# # The cache row, answered: it works in a process and not across one (2026-10-20)
#
# `drvprof cache`, both drivers, two invocations each so the second loads what the first wrote.
# Load average 16.5, so these are compile times on a contended CPU -- but both drivers ran back
# to back and the ratios are forty to a hundred fold.
#
#   microseconds, per vkCreateGraphicsPipelines      fs-const    fs-alu    fs-tex
#   BLOB   run 1, empty cache, first create             7582      8874     12972
#          run 1, repeats against that cache              88        91       112
#          run 2, cache preloaded, first create          6229     15800     13268
#          run 2, repeats                                 205       176       112
#   TURNIP run 1, empty cache, first create             2276      1606      4798
#          run 1, repeats                                  5.2       5.3       5.7
#          run 2, cache preloaded, first create           77        27        48
#          run 2, repeats                                  20        20        21
#
# **The blob honors a cache object within a process**: 88 us against 7582 for the same pipeline,
# an eighty-fold drop. #151's "no cache behind `vkCreateGraphicsPipelines`" was the absence of a
# cache object and nothing more, as the correction in #152 said.
#
# **And its serialized data does not carry across a process.** Run 2 loaded the 12,808 bytes run
# 1 wrote, and still paid 6.2 to 15.8 ms for the first create of every shader -- full recompiles.
# `vkGetPipelineCacheData` then returned **25,593** bytes, twice what went in, so the loaded
# entries were kept and not matched: the blob appended new ones beside them.
#
# Turnip's does carry: 27 us where a compile is 1606, and its cache came back the same 28,573
# bytes it went in as, so every entry was recognized.
#
# **What that costs us.** This crate builds 168 pipelines. On the blob that is one to two seconds
# of compile on **every process start**, and a cache shipped with the application does not avoid
# it -- only keeping the process alive does. On turnip the same cache makes it a few milliseconds.
# For a product that starts a map once and runs for hours, this is a startup-latency question
# rather than a frame-rate one; for anything that respawns, it is the whole cost.
#
# # And the 40% fragment-ALU gap was the loop, not the ALU
#
# #151 reports turnip 40% behind on 256 dependent multiply-adds and guesses at multiply-add
# fusion. The guess was wrong and so was the framing. Two more shader pairs say why.
#
#   microseconds, GPU timestamps, min of fifteen, both drivers back to back
#
#   fragment shader                              blob   turnip
#   256 mads, rolled loop  (fs-alu)             2253.7   3156.3     turnip 40% slower
#   the same, written flat (fs-alu-flat)         140.4    768.3     see below
#   256 squarings, rolled  (fs-sq)              2157.6   3158.2     turnip 46% slower
#   the same, written flat (fs-sq-flat)          440.5    447.8     **level, 1.7%**
#
# `fs-sq` squares rather than scaling, which no compiler can fold -- `acc * k + c` repeated is
# affine and collapses to one multiply-add, `acc * acc + c` does not. That pair is the one that
# measures arithmetic:
#
# **Unrolled, the two drivers are within 1.7% of each other.** The ALU is not turnip's weak
# point. What is 46% slower is the *rolled* form of the same arithmetic.
#
# `IR3_SHADER_DEBUG=disasm` says what ir3 did, per fragment shader:
#
#   shader           instr   nops   non-nops   loops
#   fs-const             5      0          5       0
#   fs-alu              30     15         15       1   <- not unrolled
#   fs-alu-flat       1038    774        264       0
#   fs-sq               30     15         15       1   <- not unrolled
#   fs-sq-flat        1042    777        265       0
#   fs-tex             158      6        152       0   <- sixteen iterations, unrolled
#
# So ir3 unrolls a sixteen-iteration loop and leaves a 256-iteration one rolled, and the rolled
# form pays loop overhead on top of the stalls a dependent chain causes either way -- three
# quarters of the flat form's slots are nops too. The blob's compiler handles the long loop
# better; given the same straight-line code they are equal.
#
# **The affine pair measures something else again.** The blob returns 140.4 us for `fs-alu-flat`,
# which is exactly its cost for a constant color: it folded 256 affine steps into nothing.
# Turnip kept all 256 (1038 instructions) and took 768.3. So Qualcomm's compiler does an
# algebraic simplification turnip does not -- a real difference, on a shape no shader in this
# crate has.
#
# **What this means for us.** Nothing in these families loops 256 times; the longest is a 3x3
# kernel in `hillshade_prepare` and a sixteen-tap raster, and sixteen is the count ir3 unrolls.
# So the 40% in #151 does not describe any shader we ship, and the ALU rate on this part is the
# same whichever driver draws it.
#
# ---------------------------------------------------------------------------
# # What a first frame costs: 8 to 36 milliseconds a pipeline on the blob (2026-10-20)
#
# The sections above measure compilation with shaders of 88 to 358 words, which is a tenth of
# what this crate emits. `drvprof module <vs.spv> <fs.spv> ...` takes **per-stage** SPIR-V --
# naga with `PipelineOptions`, one entry point at a time, which is what `pipelines::Stages`
# does and what the blob requires -- so the figures below are real family modules.
#
#   microseconds, per vkCreateGraphicsPipelines, no cache object
#
#   family (vertex + fragment words)        blob cold   blob p50   turnip cold   turnip p50
#   background          (1072 + 946)         9810..14588    8370      3380..6299      5.9
#   fill_extrusion      (1886 + 1039)       20051..20257   19830      8116..8846      6.2
#   line_sdf            (2885 + 1810)       34893..36016   30700     14598..14998      6.2
#
# **Three to five times what the synthetic shaders suggested.** `line_sdf` is 35 ms a pipeline on
# the blob -- a single family, compiled once per process, and the blob's p50 equals its cold
# figure because without a cache object it recompiles every time, and with one the data does not
# survive the process (the section above).
#
# **Turnip compiles the same modules 2.4 to 2.5 times faster** and then answers repeats in 6 us
# from its in-process cache, with Mesa's disk cache disabled.
#
# ## The number that matters
#
# `capture_frame` against a real captured frame (`real.tslcap`, a Mercator view of a city) needs
# **12 pipelines from 7 families**: background, circle, fill, fill_extrusion,
# fill_extrusion_instanced, fill_outline_triangulated, line. Not the 168 that `pipelines_build`
# brings up -- `Cache` builds what a frame asks for.
#
# So the shader compile before a first frame, on this part:
#
#   blob     12 pipelines x 8..35 ms   =  roughly a quarter of a second, every process start,
#                                        and no cache avoids it
#   turnip   12 x 3.4..15 ms the first time, then ~0 with a cache persisted to a file
#
# A product that starts a map once and runs for hours pays the blob's quarter second at startup
# and never again. Anything that respawns the renderer pays it every time, and that is the one
# place in this whole comparison where the two drivers are not close.
